ESP32-C6 · RTC_SLOW calibration · espressif/esp-idf#19250

MIN_SLP_MS threshold sweep: results

13 runs (2026-10-20 10:52 to 2026-10-21 14:24 UTC) of CONFIG_PM_LIGHTSLEEP_RTC_OSC_CAL_AFTER_WAKEUP_MIN_SLP_MS against stock ESP-IDF. The clock error grows with the threshold at every step. A threshold of 0 (calibrate after every wake) is best in every view. It halves stock's error: +462 against +1015 ppm unheated, +418 against +868 ppm heated. A follow-up run with varied work windows (10, 10, 200, 200 ms; section 6) replayed every policy on the same 10 h of sleeps: still monotonic with 0 best (+346 against stock +755), including the case built to favour a threshold.

1. Setup

  • Board: Seeed XIAO ESP32-C6. RTC_SLOW = internal RC (tempco about −1540 ppm/°C). CPU 160 MHz, FreeRTOS 1 kHz tick, automatic light sleep (tickless idle, IDLE_TIME_BEFORE_SLEEP=2).
  • ESP-IDF: master with the PR branch fix/rtc-slow-cal-after-wakeup @ 5f666735c6 (the MIN_SLP_MS sub-option, not pushed). "stock" = CONFIG_PM_LIGHTSLEEP_RTC_OSC_CAL_AFTER_WAKEUP off.
  • Reproducer: tools/rtc_slow_cal_repro (branch feat/rtc-cal-repro, sweep built from 36d5659). Sleeps are random and log-uniform from 1 ms to 10 s, with a fixed seed of 0x19250, so every run sees the same sleep sequence. After each wake there is a fixed 200 ms active window: report line and die temperature first, then a busy loop to the end.
  • Reference: the host's CLOCK_MONOTONIC stamps each UART line (USB-UART on GPIO16), minus the line's wire time. Positive ppm = the device clock runs fast.
  • Runs: 70 min each, one firmware per threshold. Only minutes 10–70 are analysed (clock_drift.py fit --skip 600 --length 4200), so every run covers the same 2,380 or so sleeps of the sequence.
  • Pass 1 (runs 1–8) was heated on purpose: the user put the chip on a hot surface for part of each run (die up to 40–43 °C) to simulate real temperature drift. Pass 2 (runs 9–13) was not heated: die 24.6–27.0 °C.
  • Log: logs/2026-10-20__min_slp_sweep_busy200__uart.log (all 13 runs; each one starts with a REPRO … mode= banner).

4. What the data shows

  1. The threshold only swaps rows between two populations of readings. Across all 13 runs, the fix builds' cells reproduce at about the SE level, heated or not. In the 1–10 s column: entry after 1–10 ms, +1150 (sd 42, 9 runs); entry after 10–100 ms, +1345 (sd 56, 6 runs); post-wake after 0.1–1 s, +462 (sd 35, 7 runs); post-wake after 1–10 s, +160 (sd 46, 11 runs). So the matrix for any threshold is the post-wake rows above T plus the entry rows below T. That rule predicted runs 4–8 and pass 2 within about ±70 ppm.
  2. Every entry cell is worse than the post-wake cell in the same row, by +230…+790 ppm for long sleeps (the gap grows with the previous sleep, because a longer previous sleep makes the post-wake reading colder). So raising the threshold can only add error, which is why the result is monotonic with 0 as the optimum.
  3. Mechanism: the die heats locally during each active window. The error of a sleep ≈ mean RC frequency during the sleep − RC frequency at the calibration. The entry reading comes at the end of the window, the hottest point. The post-wake reading comes at the end of the previous sleep, after cooling. The heat fades over 0.1 s to a few seconds (+920 after a sleep under 100 ms, +462 after 0.1–1 s, +160 after 1–10 s). At constant ambient (pass 2), the entry-vs-post-wake difference after a short sleep is about +230…+430 ppm, i.e. 0.15–0.3 °C. The whole swing of about 1400 ppm is about 0.9 °C. Both are below the 1 °C resolution of the die sensor, which reads 25–27 °C throughout.
  4. The premise of MIN_SLP_MS is backwards. Its help text says that after a short sleep the chip has not cooled yet, so it should calibrate at entry. But the entry reading is even warmer: the work after the wake only adds heat.
  5. Over-correction is small and threshold-independent. A cold reading (after a 1–10 s sleep) applied to a 0.1–1 s sleep that starts hot gives −165…−335 ppm. Stock's same cell is +460, so post-wake is still the smaller error. That row is post-wake for every T < 1 s, and it adds only −2…−5 ppm overall.
  6. Heating changes stock, not the fix. Stock moved from +868 (heated) to +1015 (unheated); the fix builds moved −71…+64 with no common direction.
Unexplained: stock's entry cells don't match the fix builds' entry cells, even though the entry code path is the same with the option on or off (sleep_modes.c 801–813, the same rtc_clk_cal + esp_clk_slowclk_cal_set). Run 9 (unheated) sits +216 / +79 / +50 ppm above the pooled fix entry cells; run 1 (heated) sits +67 / −145 / −147 off. There is one stock run per condition, so this may be a run-level offset (run 9 came right after heated run 8). It changes no conclusion: even 200 ppm lower, stock is the worst.

5. Conclusion for the PR

  • No accuracy reason for MIN_SLP_MS > 0 showed up in any condition. The only effect of the threshold is moving one calibration (10 RC cycles, about 70–80 µs, estimated and not measured) out of the wake path for sleeps shorter than T. There is one calibration per sleep either way, so it saves no energy.
  • Options: (a) remove the sub-option and always calibrate after a wake with rtc_time_diff > 0 (recommended); (b) keep it with default 0 and a help text that presents it as a wake-latency trade-off that costs accuracy. Decision pending.

Remaining error at T = 0, and a possible follow-up (outside #19250)

About 75 % of T = 0's +462 ppm comes from long sleeps after a sleep under 100 ms (+918 average, 311 of 653 long sleeps, about 37 % of wall time): the post-wake reading after a short sleep is still warm. One idea is to reuse, after a sleep under about 100 ms, the last post-wake reading taken after a long sleep. Estimate: +462 → about +240 ppm. Calculated from the cells, not measured.

6. Follow-up: varied work windows and offline replay

In the sweep every active window was 200 ms. The case that might favour a threshold never occurred: a long window, a short sleep, then a short window before a long sleep. There the post-wake reading (taken at the start of the short window) is still warm from the long one, so the entry reading might not be much worse. This run tests that case.

Setup

  • Firmware: feat/rtc-cal-repro @ 8f9a406, same ESP-IDF as the sweep. The work windows cycle through k_busy_ms[] = {10, 10, 200, 200} (in main/rtc_slow_cal_repro.c), independently of the seeded sleep sequence, so every pair of windows meets every sleep bin.
  • The app takes both readings itself, each rtc_clk_cal(CLK_CAL_RTC_SLOW, 10) like ESP-IDF: e in a PM enter callback (just before esp_light_sleep_start(), kept only if the sleep really happened) and w in the exit callback (right after the wake). The report line gains e=, w= and b= (the window that follows).
  • Offline replay (clock_drift.py fit|matrix --replay stock 0 10 50 100 1000): one run gives every policy on the same sleeps. For each sleep, the period the policy would have used is w of the previous wake if the previous sleep was longer than T, else e; the device time is corrected by s · (P′/c − 1), where c is the period ESP-IDF actually used.
  • Runs, unheated, log logs/2026-10-22__busy_pattern_replay__uart.log:
    • Run 1, T = 0: 2026-10-21 19:09:40 to 2026-10-22 05:29, 617.5 min, 31,508 lines, all lines analysed (--skip 0). Die 21.3–29.1 °C (mean 23.2); the room cooled overnight.
    • Run 2, stock: from 2026-10-22 05:30:20, minutes 10–77 analysed (66.7 min, 3,247 lines). Die 24.0–26.0 °C (mean 24.7).
    • A first T = 0 run (2026-10-21 16:17–18:12, logs/2026-10-21__busy_pattern_replay__uart.log) ended with a host reboot and is not used here. Its 103 min gave the same picture (measured +363, replay 0 +356, 100 +516, stock +740).

What it shows

  1. The warm post-wake reading is real. At T = 0, a long sleep after 200 → short sleep → 10 is worse than after 200 → short sleep → 200 (+930 against +836, +856 against +628). The reading comes from the start of the 10 ms window and still carries the 200 ms window's heat, but the sleep that follows starts cooler than after another 200 ms of work.
  2. The entry reading is warmer still, so a threshold does not help there either: T = 100 adds +132 ±21 ppm in that case. The 10 ms window alone adds about +100 ppm between w and e, whatever came before (200 → 10 ≈ 10 → 10), more than the +5…+50 predicted.
  3. No work pattern makes T > 0 better. The threshold loses in all four, by 4.9 SE or more. The remaining T = 0 error after short sleeps needs a colder reading (the follow-up idea in section 5), not an earlier one.
Host-timing artifact, absolute cells only: when a 10 ms window is followed by a 1–10 ms sleep, the next line reaches the host late (median +3 ms, worst 10 % beyond +25 ms; all other cases within about ±0.5 ms). The 87-character line needs 7.6 ms on the wire and is probably not fully sent before that short sleep. This inflates the absolute cells of every row whose window before the previous sleep was 10 ms (pairs 10 → 200 and 10 → 10, previous sleep 1–10 ms: about +1800 ppm even in long sleeps), so those cells are not shown. It affects only those lines' stamps: the paired differences above and the 10-hour fits are unaffected (replay and measured agree within 3.5 ppm).

7. How to reproduce the numbers

cd tools/rtc_slow_cal_repro
L=../../logs/2026-10-20__min_slp_sweep_busy200__uart.log
uv run --script clock_drift.py fit    $L --skip 600 --length 4200
# matrices per pass: cut the log at 2026-10-21T08:15 (pass 1 before, pass 2 after)
awk '$1 < "2026-10-21T08:15"'  $L > pass1.log
awk '$1 >= "2026-10-21T08:15"' $L > pass2.log
uv run --script clock_drift.py matrix pass2.log --skip 600 --length 4200 --order threshold

# section 6: run 1 (T = 0) is everything before the stock banner at 2026-10-22T05:30
L=../../logs/2026-10-22__busy_pattern_replay__uart.log
awk '$1 < "2026-10-22T05:29"' $L > run1.log
uv run --script clock_drift.py fit    run1.log --skip 0 --replay stock 0 10 50 100 1000
uv run --script clock_drift.py matrix run1.log --skip 0 --unit ppm --order threshold --replay 0 100 --work 200,10   # also 200,200 10,200 10,10
uv run --script clock_drift.py fit    $L --skip 600 --replay stock   # run 2 (stock) segment: measured vs replay

The paired T = 100 − T = 0 values are the mean of (e(i) − w(i−1)) / c(i) over the selected sleeps (both lines k=1), computed outside the script. The duration-weighted means equal the matrix cell differences within a few ppm. Plan and run notes: tickets_and_plans/plan_busy_pattern_replay.html (local).
